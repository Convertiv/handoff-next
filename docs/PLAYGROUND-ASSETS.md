# Design — closing the asset loop (Phase 3)

**Status:** proposed, 2026-07-30.

Today a page the chat builds has labelled grey placeholders where its pictures should be. The library
is searched first and real assets win when they exist, but when nothing matches, the placeholder is
where it ends. Phase 3 is the rest: generate the missing image, **put it in the library**, and let the
page pick it up.

## The constraint that decides the design

Generation cannot happen inside the chat turn.

| | |
|---|---|
| Playground route budget | `maxDuration = 120` |
| Cron pickup latency | up to 60s (`* * * * *`) |
| `openAiImageEdit` | ~25s typical, up to 4 minutes at high quality |

One image blows the budget on pickup latency alone. Two is not close. And `generate-design`'s existing
answer — hold the response open and await the worker inline — costs a request held open for minutes and
does not survive the user closing the tab.

So the turn must **not wait**, which turns out to be the better product anyway.

## The shape: propose now, fill in after

1. The chat searches the library. Real asset found → use it, as today.
2. Nothing matches → it calls `request_image`, and the server **enqueues a job and returns the
   placeholder immediately**.
3. The proposal completes with placeholders in it and is applied to the canvas straight away. The page
   is usable in seconds, not minutes.
4. The client polls the pending jobs. Each one that lands is **already an asset in the library**; the
   client swaps that placeholder's `src` on the canvas in place.

The user gets a whole page immediately and watches the pictures arrive. That is a better experience
than a spinner, and it falls out of the constraint rather than fighting it.

**Placeholders are the fallback, not a failure state.** If a job fails or the user leaves, the page
still holds a labelled placeholder — exactly what it has today. Nothing regresses.

## Reusing the design-jobs table

`handoff_design_generation_job` already has status/stage/error, a cron drain, ownership, poll endpoints
and admin visibility. A second table would duplicate all of it. Instead `request_params.intent` gets a
value:

- `intent: 'artifact'` (absent = today's behaviour) → the existing `runDesignGenerationJob`.
- `intent: 'asset'` → a new `runAssetGenerationJob`.

The `run` route branches when draining. Two reasons this is not just laziness: the playground inherits
the reaper and the poll endpoints for free, and one queue means one place to look when generation is
backed up.

**It needs its own worker body, not a flag on the old one.** `runDesignGenerationJob` builds a
design-artifact prompt — foundation sheets, component references, iteration bases — and auto-creates a
`Draft — <date>` artifact when `artifactId` is null. A content photo for a hero wants none of that, and
littering the design library with drafts from playground turns would be a bug, not a side effect.

## The piece that does not exist yet

Nothing in the codebase turns generated bytes into a library asset. `openAiImageEdit` returns a base64
data URL; `insertAsset` writes a row and never touches bytes; the only code that re-hosts remote bytes
is Figma-specific.

`storeImageAsset` composes the pieces that already exist — content-hash id, `sharp` thumbnail, S3 or
the Postgres blob fallback, `insertAsset` — into the one function both halves of this phase need.
Phase 3's second bullet, ingesting an attachment or a URL-pulled image, is the same function with a
different byte source. Writing it once is the whole reason it is its own module.

Storage follows whatever the deployment already does: S3/CloudFront when configured, base64 in Postgres
otherwise. Not a new decision.

## The `seenAssetSrcs` trap

`mergeBlockValues` strips any image src the model did not get from a real search result — the fix for
it inventing `https://assets.8x8.com/images/...`. A generated asset's URL has to be added to that set
in the same turn or the guard will throw away the thing we just made. The guard is right and stays;
`request_image` registers its placeholder (and, later, the real src) explicitly.

## Scope

**In:** `request_image` tool · `intent: 'asset'` jobs · `runAssetGenerationJob` · `storeImageAsset` ·
client polling and in-place swap · a reaper for jobs stuck in `running`.

**Out:**
- **Regenerating an image you do not like.** Wants the changeset vocabulary and a prompt to edit; a
  separate turn of work.
- **URL/attachment ingest.** `storeImageAsset` is built to serve it, but wiring the two entry points is
  its own change and the chat currently sends scraped images as alt text only, on purpose.
- **Cost controls beyond a per-turn cap.** Images are the most expensive thing here by an order of
  magnitude; a hard cap per turn goes in now, budgets can come later.

## Risks

- **A job stuck in `running` is currently never reaped** — the existing reaper only covers artifact
  statuses. One producer made that survivable; two makes it worth fixing, and it is a few lines.
- **Cost.** A page wanting six images is six generations from one sentence. Cap per turn, and say in
  the UI what is being generated before it runs.
- **Swap-after-apply races the user.** They may edit or delete the block while its image is generating.
  The swap must verify the block is still there and still holds that placeholder — the same
  expect-check the edit operations already use, for the same reason.
